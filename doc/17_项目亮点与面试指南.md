## ② 架构与演进

### 2.1 三个可部署单元,一个业务大脑

| 单元 | 端口 | 职责 |
| --- | --- | --- |
| `cloud` | gRPC :8081 | **全部业务逻辑,唯一写 DB / Redis / 物理存储的组件** |
| `gateway` | HTTP :8888 | 纯 REST↔gRPC 协议转换,零业务逻辑(46 条映射,口径:service.proto 46 个 rpc) |
| `web` | HTTP :8080 | 静态前端 + `/api` 反代,把 Authorization 头桥接为 gRPC metadata |

模块地图(证据:`cloud/internal/svc` 装配、`cloud/main.go` 拦截器链 Recovery→限流→JWT→用户状态注入):

```
浏览器 → web/server.go(反代) → gateway(REST→gRPC) → cloud 拦截器链
       → internal/server(纯委托) → internal/logic(业务,按 user/file/bucket 分包)
                                    ├→ internal/repository(唯一 DB 访问层,ent)
                                    ├→ internal/pkg/cache(唯一 Redis 访问层,nil 安全)
                                    └→ internal/pkg/storage(唯一物理存储访问层,Driver 接口)
```

**为何单体业务服务 + 薄网关,而不是一上来拆微服务**:对象存储的核心复杂度在
**元数据与物理文件的一致性**(配额、秒传共享路径、分片合并),这些状态天然同库同事务。
拆服务只会把事务边界变成网络调用,换来的是分布式一致性难题而非扩展性。
所以我选了"逻辑分层做透、物理拆分留缝"。

**未来拆分缝(面试常问"如果流量涨 100 倍")**:
1. **网关已是独立进程**——水平扩容无状态,现成;
2. **下载/流式链路可最先拆**(读多写少,`download_by_share_stream_logic.go` 的
   server-streaming 已是独立 RPC,拆出去不碰元数据事务);
3. **缩略图可异步化为独立 worker**(现同步生成 + 按需自愈,
   `internal/pkg/thumb`,拆分只需把生成动作改为队列消费);
4. **repository 接口层已隔离 DB 访问**——若元数据要分库,改 repository 不动 logic。
   这三条缝都是"现在代码里已经存在边界",不是画饼。

## ③ 并发正确性设计:8 条不变式(全篇最硬核部分)

> 逐条「问题 → 方案 → 证据」。证据 = 具体 `文件:行号` + 验证测试。
> 前 3 条有真 MySQL 并发测试(`DB_IT=1 go test ./internal/repository/ -count=1 -race`,默认跳过,
> 独立测试库 `cloud_it` 自动创建,见 `it_test.go:38-83`)。

### 3.1 配额优先记账(§5.1)

- **问题**:若"先写文件记录、后扣配额",进程在两步之间崩溃,桶容量永久漂移(记录在、配额没扣,超卖);反之先扣后写,崩溃则用户白扣。顺序本身不解决崩溃,但决定了崩溃后的补偿动作是否简单可靠。
- **方案**:上传与分片合并都**先原子扣桶容量**——`TryIncUsedSize` 是单条条件 UPDATE(`used_size + delta <= size_limit` 才生效,失败即拒绝),后续任一步失败走统一 rollback **补偿性归还**;归还同样不越零。
- **证据**:`cloud/internal/repository/bucket.go:155`(`TryIncUsedSize`)、`bucket.go:178`(`TryDecUsedSize`);调用顺序见 `cloud/internal/logic/file/upload_file_logic.go`(先扣配额再写物理/记录)。
- **测试**:`cloud/internal/repository/it_test.go:103` `TestTryIncUsedSizeConcurrentQuota`——**50 个协程并发争抢**,上限 1000、每步 100,断言成功数**恰好 10 次**且终值 `used_size == 1000`:多一次=超卖,少一次=漏记,双向都测;`it_test.go:146` `TestTryDecUsedSizeFloorGuards` 断言超额归还拒绝且账目零改动、归还到零后继续归还被拒(永不为负)。

### 3.2 Complete 合并权门闩(§5.2)

- **问题**:分片上传的 Complete 接口若被并发调用(客户端重试/双击),同一 upload_id 会重复合并、重复扣配额、产生双份物理文件。
- **方案**:`file_parts` 行做 **uploaded→merged 一次性状态迁移**,`TryMarkMerging` 只有把全部所需分片从事务内改成 merged 的一方拿到"合并权";所有失败路径必须 `RestoreUploaded` 恢复,保留客户端重试能力。
- **证据**:`cloud/internal/repository/file_part.go:118`(`TryMarkMerging`)、`file_part.go:134`(`RestoreUploaded`)、`file_part.go:89`(`CountUploaded`,完整性判定以 DB 状态机为唯一基准)。
- **测试**:`it_test.go:200` `TestTryMarkMergingExclusiveGate`——30 个并发 Complete 模拟,断言**恰好 1 个独占成功**,且门闩后 10 条分片全为 merged;再验证 RestoreUploaded 后可重新占有(失败可重入)。

### 3.3 秒传共享物理路径(§5.3)

- **问题**:秒传让多条 File 记录指向同一物理文件(跨桶/改名)。删除其中一条若直接删物理文件,**会删掉别人的数据**——这是数据丢失级 bug。
- **方案**:物理删除必须走 `DeletePhysicalIfUnshared`(引用计数守卫:还有其他 File 记录引用该路径时只删记录不删文件);秒传命中要求 MD5 **且 size 一致**,防止哈希碰撞误共享。
- **证据**:`cloud/internal/repository/file.go:309`(`DeletePhysicalIfUnshared`);秒传 Redis→DB 兜底与共享路径逻辑在 `cloud/internal/logic/file/upload_file_logic.go:117-131,154`。
- **测试**:回收站闭环与秒传断言在 E2E 冒烟覆盖(`scripts/smoke_e2e.py` 35 项,见 §⑥)——此条依赖业务库多表状态,DB_IT 用独立空库模拟代价高,如实说明覆盖层级在 E2E。

### 3.4 限流身份键不可伪造(§5.4)

- **问题**:若用 Authorization 原文或客户端可传的字段当限流键,攻击者每次请求随机换一个键即可绕过限流。
- **方案**:限流键 = **JWT 验签之后**的 user_id(伪造 token 过不了验签,只会落进匿名 IP 桶);匿名取网关转发的 XFF 首跳,文档明确标注"可伪造、仅尽力分桶,生产应置于可信代理后";限流桶有 10 万上限与 30 分钟空闲回收(防内存被海量 IP 撑爆)。
- **证据**:`cloud/internal/middleware/ratelimit_middleware.go:21-25`(设计注释)、`:134-137`(`identityKey`)。
- **测试**:`cloud/internal/middleware/ratelimit_test.go`(身份键提取与溢出桶回收)。

### 3.5 登录锁定键是用户 ID(§5.5)

- **问题**:本项目手机/邮箱注册用户的 username 为 NULL——若用 username 作锁定键,全体该类用户共享同一个计数桶:锁定阈值失真,且**任何人能把所有手机号用户集体锁死**( DoS 放大)。
- **方案**:失败计数键统一用内部用户 ID,锁定 fail 路径收敛到 `loginWithLookup`(先查出 ID 再计数)。
- **证据**:键设计见 `cloud/internal/pkg/loginlock/loginlock.go`(注释 :65-66 说明降级语义),fail 路径在 `internal/logic/user` 的 `loginWithLookup`。
- **测试**:`cloud/internal/pkg/loginlock/loginlock_test.go`(含 Redis 故障降级用例)。

### 3.6 会话版本化(§5.6,P24)

- **问题**:JWT 无状态,重置密码/禁用账号后,已签发的 token 在过期前依然有效——账号被盗后"改密码踢不掉攻击者"。
- **方案**:`users.token_version` 单调递增字段(`ent/schema/user.go:60`),签发时内嵌 ver,网关侧 `jwt_middleware` 每次请求与 DB 比对(`internal/middleware/jwt_middleware.go:160` `verFromContext`),落后即拒——重置密码/禁用/**角色变更**都 `AddTokenVersion(1)` 即时踢出全部会话;DB 比对结果带 60s 用户状态缓存,在安全与 DB 压力间取舍。
- **测试**:会话版本比对逻辑在 JWT 中间件链路,E2E 冒烟覆盖登录/锁定/429(§⑥);P24 提交 a5461f5。

### 3.7 降级语义矩阵(§5.7)——单列,见 ④

### 3.8 信任边界与路径安全(§5.8)

- **问题**:对象存储最经典的漏洞是**路径穿越**(`../../` 逃出存储根目录)与匿名接口信任注入头(伪造 XFF 洗白审计)。
- **方案**:物理文件名/路径必须过 `ValidSuffix` + `ValidStorageID` + `SafeJoin`(白名单正则 + Join 后校验根内);匿名接口只信任**网关注入**的 `gateway-*` 前缀 metadata,XFF 明确标注可伪造、审计仅作参考;内部错误一律 `response.ErrInternal`(细节只进日志,不泄漏给客户端)。
- **证据**:`cloud/internal/pkg/storage/safe_path.go:21,24,27`;错误码契约在 `internal/pkg/response/codes.go`(10xxx 用户/20xxx 桶/30xxx 文件分享/40xxx 存储/42900 限流)。
- **测试**:`internal/pkg/storage/safe_path_test.go` + `local_driver_test.go`(路径安全与 Put/合并);JWT **alg=none 算法混淆攻击**拒绝测试在 `internal/pkg/jwt/jwt_test.go:48-55`(白名单 HMAC,keyfunc 拒绝未签名 token,实现 `internal/pkg/jwt/jwt.go:97`)。

## ④ 可靠性:Redis 故障降级矩阵

> 讲点:**降级不是一刀切**。我按"该能力离了 Redis 还剩多少正确性"逐个做了决策,
> 每行都有明确行为与取舍理由(出处 doc/15 §5.7,实现见各文件):

| 能力 | Redis 不可用时 | 为什么这样取舍 |
| --- | --- | --- |
| 秒传索引 | 跳过 Redis,直接查 DB(`repository.GetByMD5`,file.go:53) | DB 本就是权威数据,慢一点但零错误;Redis 只是加速层 |
| 登录锁定 | 进程内计数兜底(`loginlock.go:32,65-66`);多实例阈值放宽为 阈值×实例数,限频告警(:120 防故障风暴刷日志) | 单实例语义完整;多实例变"尽力锁定"——明确告知这是**语义放宽而非失效**,是诚实工程 |
| 分享下载计数 | DB 兜底:查记录校验 max_count 后原子自增;DB 也不可用则放行并记失计 | 计数是限次能力,Redis+DB 双层兜底;双层都挂宁可放行不阻断用户,失计可审计 |
| 分片状态 | DB 是唯一基准,Redis parts 仅加速(命中会回查修复 DB) | **完整性绝不依赖缓存**——这是 3.1/3.2 正确性的延伸 |
| 验证码 | 返回明确「服务不可用」错误,**无降级** | 验证码语义(60s 频控/10 条日配额)完全建立在 Redis TTL 上,伪造降级反而引入弱安全 |

**统一实现层**:`internal/pkg/cache/doc.go:3-4` 写死两条硬约定——client 为 nil(未配置 Redis)时读方法返回零值/未命中、写方法返回可识别错误(`kv.go:25` 等),**绝不 panic**。所以"无 Redis 可跑通全链路"不是巧合,是架构约束:35 项 E2E 无 Redis 亦可运行,顺带验证全部降级路径(冒烟脚本头部注释明确此设计)。

**面试话术**:"我做降级设计时先问一个问题:这个数据谁是权威?Redis 只是权威数据的缓存或加速,就降级到 DB;Redis 本身承载语义(如验证码 TTL),就明确拒绝而不是假装成功。降级矩阵里没有一行是'抛异常',也没有一行是'静默吞掉'。"

### E2E 抓出 5 个真实缺陷(重点故事,出处 git log b900bc7 + df10cbf)

1. **直传首传必 panic(批次 5a 引入的回归)**:秒传未命中时 `instantSrc.Path` 在 nil 检查前解引用,第一次上传必 500——单测全绿,只有真实链路首传才触发。这是"为什么 E2E 要跑真实服务"的最好注脚:**mock 不会替你犯真实世界的错**。
2. **`/file/info` 网关映射 POST,前端/README 契约是 GET**:存量 bug,前端 `getFileInfo` 一直 405,前端开发已经习惯了绕路——契约漂移靠人眼发现不了。
3. **`Storage.DirectUploadSize` 默认值被回落逻辑吞掉**:json optional 无法区分"未配置"与"配置为 0",默认值永远失效——配置语义 bug。
4. **列表排序参数缺 `ignore_empty`**:sort_by/sort_order 的 in 校验把"不传排序参数"的请求全部判为参数校验失败——**前端恒传参掩盖了这个问题**,任何 API 调用方都会踩(这也是 doc/15 陷阱清单 §七 明确写入变更流程的原因)。
5. **`visibility` 必填误设**:创建桶不传 visibility 被拒,与 ent schema 默认 private 的语义冲突。

**讲法**:"这 5 个缺陷分三类:回归(1)、契约漂移(2/4/5)、配置语义(3)。每一类 mock 测试都天然测不到——回归需要完整调用链,契约漂移需要网关真实路由,配置语义需要真实启动。所以我的结论是:单元测试保证逻辑,E2E 保证系统,**两层的缺陷集合不相交,不能互相替代**。"

## ⑧ 高频追问预演

**追问 A(对 ③1/③2):为什么不用 Redis 分布式锁?**
→ 答方向:分布式锁引入了锁服务本身的可用性问题(Redis 挂了锁就失效,恰与降级矩阵冲突),且锁是"互斥"而我要的是"条件成立才迁移"的原子语义——单条条件 UPDATE / 一次性状态迁移把互斥交给 MySQL 行锁,失败路径天然清晰(affected rows=0),还附带回滚恢复点(RestoreUploaded)。分布式锁适合多资源协调,单行状态机场景是杀鸡用牛刀且更脆。

**追问 B(对 ③1):50 协程那测试,如果配额引擎换成先 SELECT 后 UPDATE 会怎样?**
→ 答方向:SELECT-then-UPDATE 在默认 RR 隔离级别下是丢失更新,50 并发会全部读到旧 used_size 全部成功 → 超卖;这正是该测试存在的意义——它不是功能测试,是**不变式测试**,换任何实现都必须过同一断言。可以进一步讲 MySQL RR 下 UPDATE 是当前读、会加锁,所以条件 UPDATE 能成立。

**追问 C(对 ④):降级矩阵多实例下登录锁定"阈值×实例数"是不是漏洞?**
→ 答方向:是已知的语义放宽,不是疏忽——文件头注释写明这一点(loginlock.go:65-66)。修法是锁定状态挪 DB 或统一 Redis 集群,代价是引入新的可用性耦合;当前取舍是"Redis 故障期间尽力锁定 + 限频告警可观测",把选择权留给部署规模。关键讲点:**我标注了降级后的真实语义,而不是假装没变**。

**追问 D(对 ⑥):E2E 那 5 个缺陷,为什么不直接上 mock/契约测试?**
→ 答方向:契约测试(Pact 类)能抓 2/4/5 类漂移,但抓不了 1(需要真实 panic 路径)和 3(需要真实配置加载)。35 项冒烟零依赖、3 分钟能跑完,性价比高于维护一套契约框架;下一步演进方向才是给 46 个端点补契约快照。

**追问 E(对 ②):为什么 46 个端点用 goctl gateway 而不是 grpc-gateway?**
→ 答方向:go-zero 全家桶内 protoset 方式与框架生命周期一致,路由声明在 yaml 可审计;已知代价是两份网关 yaml 手工同步(doc/15 陷阱 1)+ protoset 再生成链(陷阱 3),这些代价我写进了交接文档而不是绕开。

**追问 F(对 ⑨):直传 ≤5MB 走 proto bytes,大文件怎么办?**
→ 答方向:前端 `DIRECT_MAX` 联动后端 `Storage.DirectUploadSize`(陷阱 6),>5MB 自动切分片(3 并发、断点续传);已知技术债:直传彻底流式化是 proto 大改,受 5MB 限幅风险可控,列入技术债清单(doc/15 §九 5)。
