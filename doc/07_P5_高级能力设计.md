## 二、秒传（Instant Upload）

### 2.1 当前状态

P4 阶段已在 [upload_file_logic.go](../cloud/internal/logic/file/upload_file_logic.go) 中实现 DB 级别秒传：

```go
// 仅查 DB
if exist, _ := fileRepo.GetByMD5(l.ctx, userID, md5); exist != nil {
    return response.Success(&service.UploadFileResponse{
        File: toFileMeta(exist), Instant: true,
    })
}
```

**问题**：
1. 每次上传都查 DB，秒传命中场景的延迟较高
2. 同一用户多次上传相同文件时无法快速判定
3. 客户端未传 MD5 时无法触发秒传（仅靠服务端计算后查 DB）

### 2.2 增强方案：Redis 索引 + DB 兜底

#### 2.2.1 Redis 键设计

```
md5:{user_id}:{md5}  →  file_id      (TTL: 30 天)
```

- 命中即返回 `file_id`，避免 DB 查询
- 未命中则回退 DB 查询（兜底）
- DB 命中后回写 Redis（重建索引）

#### 2.2.2 写入时机

| 时机 | 动作 |
| ---- | ---- |
| 普通上传成功 | 写 DB 后写 Redis `md5:{user_id}:{md5} = file_id` |
| 分片上传合并成功 | 同上 |
| 文件复制成功 | 复制后的新文件 MD5 与源一致，写新 file_id（不覆盖旧值） |
| 文件删除成功 | 删除 Redis 索引（仅当 value 等于被删 file_id 时删，防误删） |

#### 2.2.3 校验流程

```
┌────────────────┐
│ 上传请求(含MD5)│
└───────┬────────┘
        ▼
┌────────────────────┐    命中    ┌──────────────────┐
│查 Redis md5:{u}:{m}│ ────────▶ │校验 file_id 仍存在│
└───────┬────────────┘            │ → 返回 instant   │
        │ 未命中                   └──────────────────┘
        ▼
┌────────────────────┐    命中    ┌──────────────────┐
│查 DB file.GetByMD5 │ ────────▶ │回写 Redis         │
└───────┬────────────┘            │→ 返回 instant    │
        │ 未命中                   └──────────────────┘
        ▼
   正常上传流程
```

### 2.3 实现位置

新增 `internal/pkg/cache/md5_cache.go`：

```go
// MD5Cache MD5 秒传索引缓存
type MD5Cache struct {
    client *redis.Client
    ttl    time.Duration
}

// Get  获取 MD5 索引对应的 file_id
func (c *MD5Cache) Get(ctx, userID, md5) (string, error)
// Set  写入 MD5 索引
func (c *MD5Cache) Set(ctx, userID, md5, fileID) error
// Del  删除（仅当值匹配时）
func (c *MD5Cache) Del(ctx, userID, md5, expectedFileID) error
```

修改 [upload_file_logic.go](../cloud/internal/logic/file/upload_file_logic.go)：
- 步骤 6 替换为「Redis → DB → 落地」三段式
- 步骤 9 写库后追加 Redis 写入

## 三、分片上传（Multipart Upload）

### 3.1 应用场景

- 文件 > 5MB 时客户端应使用分片上传
- 支持断点续传：分片可重传，不重复已成功分片
- 支持并发上传：客户端可并行上传多个分片

### 3.2 数据模型：FilePart

新建 [ent/schema/file_part.go](../cloud/ent/schema/file_part.go)：

```go
type FilePart struct {
    ent.Schema
}

func (FilePart) Fields() []ent.Field {
    return []ent.Field{
        field.String("id").Unique().Comment("分片记录主键"),
        field.String("upload_id").NotEmpty().Comment("分片上传唯一标识"),
        field.String("user_id").NotEmpty().Comment("上传用户"),
        field.String("bucket_id").NotEmpty().Comment("目标桶"),
        field.String("file_name").Comment("目标文件名"),
        field.String("file_suffix").Comment("目标文件后缀"),
        field.Int64("file_size").Default(0).Comment("目标文件总大小"),
        field.Int("part_number").Comment("分片序号(从1开始)"),
        field.Int64("part_size").Comment("分片大小"),
        field.String("part_md5").Comment("分片MD5"),
        field.String("part_path").Comment("分片存储路径"),
        field.Enum("status").
            Values("pending", "uploaded", "merged").
            Default("pending").Comment("分片状态"),
    }
}
```

### 3.3 Redis 键设计

| Key | 类型 | 用途 | TTL |
| --- | ---- | ---- | --- |
| `upload:{upload_id}:meta` | string(JSON) | 上传元信息(user_id/bucket_id/name/suffix/total_size/total_parts) | 24 小时 |
| `upload:{upload_id}:parts` | hash | 已上传分片：field=part_number，value=part_md5 | 24 小时 |

- meta 用于快速校验 upload_id 归属，避免每次查 DB
- parts 用于 `UploadPart` 时判断是否已上传（断点续传）

### 3.4 接口流程

#### 3.4.1 InitMultipartUpload

```
client → InitMultipartUploadRequest{bucket_id, name, suffix, size, total_parts}
                  │
                  ▼
         1. 校验入参 + 用户 + 桶归属 + 容量
                  │
                  ▼
         2. 生成 upload_id（雪花）
                  │
                  ▼
         3. 调用 Storage.InitPart(path, total_parts) → 物理 upload_id（驱动内部）
            （本地驱动用临时目录；MinIO 用原生 multipart id）
                  │
                  ▼
         4. 写 Redis meta（upload_id, user, bucket, name, suffix, size, total_parts）
                  │
                  ▼
         5. 在 DB 批量创建 total_parts 条 FilePart(status=pending)
            （也可懒创建，但预创建更便于统计已上传分片数）
                  │
                  ▼
         返回 InitMultipartUploadResponse{upload_id, part_size(建议)}
```

#### 3.4.2 UploadPart

```
client → UploadPartRequest{upload_id, part_number, content, size}
                  │
                  ▼
         1. 校验 upload_id 存在（Redis meta 命中；不命中查 DB 兜底）
                  │
                  ▼
         2. 校验 part_number 范围（1..total_parts）
                  │
                  ▼
         3. 检查 Redis parts hash：若已存在则直接返回（断点续传幂等）
                  │
                  ▼
         4. 调用 Storage.UploadPart(upload_id, part_number, reader, size)
            → 返回 part_md5
                  │
                  ▼
         5. 更新 DB FilePart：status=uploaded, part_md5, part_path, part_size
                  │
                  ▼
         6. 写 Redis parts hash：field=part_number, value=part_md5
                  │
                  ▼
         返回 UploadPartResponse{success=true, part_md5}
```

#### 3.4.3 CompleteMultipartUpload

```
client → CompleteMultipartUploadRequest{upload_id}
                  │
                  ▼
         1. 读 Redis meta → 获取 user/bucket/name/suffix/size/total_parts
                  │
                  ▼
         2. 校验所有分片已 uploaded（DB count 或 Redis parts 长度）
                  │
                  ▼
         3. 生成 file_id 与目标路径
                  │
                  ▼
         4. 调用 Storage.CompletePart(upload_id, target_path) 合并
                  │
                  ▼
         5. 计算合并文件 MD5（边合并边算；本地驱动可重新读取）
                  │
                  ▼
         6. 秒传检查：若 MD5 命中已有文件，删除刚合并的物理文件，复用旧记录
                  │
                  ▼
         7. 创建 File 元数据；更新 Bucket used_size
                  │
                  ▼
         8. 写 Redis md5 索引；更新所有 FilePart status=merged
                  │
                  ▼
         9. 删除 Redis meta/parts（释放空间，DB 记录保留以便审计）
                  │
                  ▼
         返回 CompleteMultipartUploadResponse{file}
```

#### 3.4.4 AbortMultipartUpload

```
client → AbortMultipartUploadRequest{upload_id}
                  │
                  ▼
         1. 校验 upload_id 归属
                  │
                  ▼
         2. 调用 Storage.AbortPart(upload_id) 清理物理分片
                  │
                  ▼
         3. 删除 DB FilePart 记录（按 upload_id 批量）
                  │
                  ▼
         4. 删除 Redis meta/parts
                  │
                  ▼
         返回 AbortMultipartUploadResponse{success=true}
```

### 3.5 异常场景与一致性

| 场景 | 处理 |
| ---- | ---- |
| 客户端中途断开 | 24h TTL 后 Redis 自动过期；DB 记录保留，可后续定时清理 |
| 同分片重传 | 第 3 步幂等返回，不重复写物理文件 |
| 合并后写库失败 | 物理文件已合并，需补偿删除 + 告警日志 |
| 合并后桶容量更新失败 | 同 P4 上传一致，仅告警不回滚（文件已落地） |
| 部分分片缺失就 complete | 第 2 步拦截，返回「分片不完整」错误 |

### 3.6 配置项

`etc/storage.yaml` 新增：

  Multipart:        # 新增

## 四、文件分享（File Sharing）

### 4.1 应用场景

- 用户生成分享链接，他人凭 share_code 即可访问（无需登录）
- 支持过期时间、下载次数限制
- 当前阶段仅返回文件元信息 + 下载 URL（预签名或临时令牌）

### 4.2 数据模型：FileShare

新建 [ent/schema/file_share.go](../cloud/ent/schema/file_share.go)：

```go
type FileShare struct {
    ent.Schema
}

func (FileShare) Fields() []ent.Field {
    return []ent.Field{
        field.String("id").Unique().Comment("分享记录主键"),
        field.String("file_id").NotEmpty().Comment("被分享文件"),
        field.String("user_id").NotEmpty().Comment("分享发起人"),
        field.String("share_code").Unique().Comment("提取码"),
        field.Enum("permission").
            Values("read", "download").
            Default("read").Comment("权限"),
        field.Time("expire_at").Optional().Comment("过期时间(空=永久)"),
        field.Int("max_count").Optional().Comment("最大访问次数(空=不限)"),
        field.Int("used_count").Default(0).Comment("已访问次数"),
    }
}

func (FileShare) Indexes() []ent.Index {
    return []ent.Index{
        index.Fields("share_code").Unique(),
        index.Fields("file_id"),
    }
}
```

### 4.3 接口流程

#### 4.3.1 CreateShare

```
client(已登录) → CreateShareRequest{file_id, permission, expire_seconds?, max_count?}
                  │
                  ▼
         1. 校验文件归属（user_id 匹配）
                  │
                  ▼
         2. 生成 share_code（8 位随机串，碰撞重试）
                  │
                  ▼
         3. 计算 expire_at = now + expire_seconds（若提供）
                  │
                  ▼
         4. 写 DB FileShare
                  │
                  ▼
         5. 写 Redis share:{code} = FileShare JSON（TTL 与 expire_at 对齐）
                  │
                  ▼
         返回 CreateShareResponse{share_code, share_url}
         share_url = "{gateway_base}/file/share/access?code={share_code}"
```

#### 4.3.2 AccessShare

```
client(匿名) → AccessShareRequest{share_code}
                  │
                  ▼
         1. 查 Redis share:{code} → 未命中查 DB → 仍不存在则报错
                  │
                  ▼
         2. 校验未过期（expire_at > now 或为空）
                  │
                  ▼
         3. 校验次数未超限（used_count < max_count 或 max_count 为空）
                  │
                  ▼
         4. 原子递增 used_count（DB 乐观锁 / Redis incr）
                  │
                  ▼
         5. 返回 FileMeta + permission（read 不返回下载 URL；download 返回预签名 URL）
```

### 4.4 安全考虑

- `share_code` 使用 `crypto/rand` 生成 8 位 Base62 串，碰撞概率极低
- `AccessShare` 加入 JWT 白名单，匿名可访问
- 若权限为 `read`，仅返回元信息；`download` 才返回下载链接
- 本地驱动不支持预签名，下载需通过 `/file/download` 走鉴权代理（暂用临时 token 方案）

## 八、风险与依赖

1. **Redis 可用性**：秒传/分片状态依赖 Redis；若 Redis 不可用，需降级到纯 DB 查询（影响性能但功能不丢）
2. **并发上传同一分片**：依赖 DB 唯一索引 `(upload_id, part_number)` 兜底；Redis parts hash 用 `HSetNX` 保证原子性
3. **合并时 MD5 计算**：本地驱动需在合并时同步计算；MinIO 驱动可通过 ETag 直接获取
4. **分享次数并发递增**：使用 Redis `INCR` 保证原子；DB 通过乐观锁兜底
