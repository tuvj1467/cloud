### 2.3 设计缺陷

| 编号 | 问题 | 影响 |
| ---- | ---- | ---- |
| D1 | 存储路径硬编码 `./cloud_storage/`，无配置化 | 无法切换存储后端 |
| D2 | 上传直接 `os.WriteFile`，无存储驱动抽象 | 难以扩展 MinIO/S3 |
| D3 | 文件未关联桶（`bucket_id` 未赋值） | 桶隔离失效 |
| D4 | 无 MD5 秒传检查 | 重复文件浪费存储 |
| D5 | 无分片上传 | 大文件不可用 |
| D6 | 上传未校验桶容量（`used_size` vs `size_limit`） | 容量超限风险 |
| D7 | `main.go` 与 `storage.go` 两个入口并存 | 易混淆 |
| D8 | Redis 初始化被注释 | 缓存能力缺失（与技术栈规则不符） |
| D9 | `etc/storage.yaml` 无 Redis、无存储配置项 | 配置不全 |
| D10 | `File` 与 `Bucket` schema 无 ent Edges 关联 | 无法级联查询 |
| D11 | JWT 密钥硬编码、无配置化 | 安全风险 |
| D12 | 上传 `content_type` 仅按扩展名推断 | 类型判断不准 |
| D13 | 删除未设计物理文件清理 | 孤儿文件堆积 |

### 2.4 规范问题

- 部分函数命名不规范：`Creat`（应为 `Create`）、`IntSnowFlake`（应为 `InitSnowflake`）— 但改动需同步调用方
- `file.go` repository 中 `db *sql.DB` 字段未使用
- `upload_file_logic.go` 直接在 logic 层调用 `os.MkdirAll/os.WriteFile`，未下沉到存储层

## 四、风险与约束

1. **ent 自动迁移**：dev 模式下 `Schema.Create` 会自动建表，schema 变更需注意字段兼容
2. **proto 重新生成**：proto 修改后需执行 `cloud/proto/generate_all.cmd` 重新生成 pb 代码
3. **网关 protoset**：proto 变更需同步重新生成 `gateway/protoset.pb`，否则 REST 路由失效
4. **数据兼容**：当前 `File` 表已有数据但 `bucket_id` 为空，需提供默认桶或数据迁移脚本
5. **并发安全**：桶容量扣减需事务 + 乐观锁（`version` 字段已就绪）
